# コミットメッセージのルール

## 書き方

```
種類: 何をしたか(日本語で短く)
```

- 頭の「種類」は英語、そのあとは日本語で書く
- 「何をしたか」は、未来の自分が履歴を見てわかるように短く具体的に
- 「なぜそうしたか」を残したいときだけ、Description欄に書く
- Issueを閉じるときは最後に `closes #番号` をつける

## 種類の一覧

| 種類 | 使うとき | 例 |
|---|---|---|
| feat | 新しい機能・ファイルを追加した | feat: 仕分けパズルの画面を追加 |
| fix | バグを直した | fix: 正解判定がずれる問題を修正 |
| style | 見た目だけを変えた(動きは変わらない) | style: ボタンの色を調整 |
| refactor | 動きを変えずにコードを整理した | refactor: 判定処理を関数に分ける |
| docs | READMEやドキュメントを書いた | docs: READMEに使い方を追記 |
| chore | 設定ファイルなど、その他の雑務 | chore: .gitignoreを追加 |

## 例

```
feat: 最初のページを追加
chore: 改行コードをLFに統一する設定を追加
feat: 学習記録をlocalStorageに保存 closes #3
```

# ブランチのルール

`main` は GitHub Pages で公開しているサイトそのもの。`main` にプッシュすると、すぐにサイトに出る。
なので、`main` はいつも「ちゃんと動く状態」にしておき、作業はブランチでする。

```
main          ●───────────────●  ← 公開中のサイト(いつも動く状態)
               \             /
feat/xxx        ●──●──●──●      ← ここで作る・試す
```

## 流れ

1. 作業を始める前に、`main` から新しいブランチを作る
2. ブランチでコミット・プッシュする(サイトは変わらない)
3. 動くのを確かめたら `main` にマージしてプッシュする(ここでサイトに出る)
4. マージしたブランチは消してよい

## ブランチの名前

```
種類/何をするか
```

- 頭の「種類」は、コミットの種類(feat, fix, style など)と同じものを使う
- 「何をするか」は日本語でも英語でもよい。空白は使わず、区切りは `-` にする

| 例 | 使うとき |
|---|---|
| feat/似た用語の比較 | 新しい機能を作る |
| fix/スマホ表示 | バグや表示崩れを直す |
| docs/ブランチのルール | ドキュメントだけ変える |

## GitHub Desktop での操作

- **ブランチを作る**：「Current branch」→「New branch」→ 名前を入れて「Create branch」
  - 作業途中の変更があるときは「Bring my changes to 新しいブランチ」を選ぶと、変更ごと移せる
- **プッシュ**：初回は「Publish branch」、2回目からは「Push origin」
- **mainに入れる**：「Current branch」で `main` に切り替え → Branch メニュー →「Merge into current branch」→ 作業ブランチを選ぶ →「Push origin」
- **慣れてきたら**：マージの代わりに GitHub で Pull Request を作ると、マージ前に変更点を一覧で見直せる

## 例外

- 1行だけの誤字直しなど、すぐ終わってサイトが壊れようがないものは、`main` に直接コミットしてもよい
